# AGENTS.md

## Проект
Это production-ориентированный проект на Django с Docker-окружением, PostgreSQL, Nginx и веб-интерфейсом на русском языке.
Главный приоритет: поддерживаемость, безопасность, предсказуемость, читаемость кода и минимизация регрессий.

Проект разрабатывается как долгоживущая внутренняя система, а не как одноразовый MVP.
Любые изменения должны быть совместимы с дальнейшим ростом проекта.

---

## Основные принципы работы

1. Не ломать существующую архитектуру без веской причины.
2. Предпочитать маленькие, безопасные, хорошо объяснимые изменения вместо “магических” больших переписываний.
3. Всегда сначала разбираться в текущем поведении, затем предлагать изменение.
4. Не дублировать логику, если в проекте уже есть сервис, селектор, репозиторий, форма, миксин или утилита, куда это естественно встроить.
5. Если в проекте уже сложился паттерн, продолжать его, а не изобретать новый.
6. Все ответы, тексты интерфейса, комментарии к архитектурным решениям и документация в проекте — по умолчанию на русском, если нет явной причины использовать английский.
7. Для UI важны аккуратность, тёмная тема, удобство админов, хорошая адаптивность и понятная структура экранов.
8. Не добавлять зависимости без реальной необходимости.
9. Не выполнять массовые переименования, если они не обязательны.
10. Не смешивать unrelated refactor с функциональными изменениями в одной задаче.

## Что Codex обязан делать перед любым заметным изменением

1. Сначала изучить:
   - структуру проекта
   - точки входа
   - связанные модели, формы, views, services, selectors, urls, templates, static
   - существующие тесты
   - docker compose, env usage, nginx, entrypoints, healthchecks, logging setup

2. Затем кратко сформулировать:
   - как сейчас работает участок
   - где именно будет изменение
   - какие риски регрессии есть

3. После этого вносить правки минимальным достаточным объёмом.

## Архитектурные правила

### Django
- Предпочитать тонкие views и fat service layer там, где есть бизнес-логика.
- Бизнес-правила не размазывать по шаблонам и не прятать в случайных util-функциях.
- Если логика связана с выборкой данных, рассматривать selectors/repositories.
- Если логика связана с действием или сценарием, рассматривать services/use-cases.
- Не тащить тяжёлую бизнес-логику в signals без сильной причины.
- Для сложных create/update flows сначала оценивать forms/formsets/services, а не писать логику прямо во view.
- Для queryset’ов думать о select_related/prefetch_related и N+1.
- Для прав доступа использовать понятную и проверяемую схему, а не размазанную логику по шаблонам.

### Templates / UI
- Не ухудшать текущий UX.
- Сохранять русскоязычный интерфейс.
- Делать интерфейс опрятным и административно удобным.
- Если меняется форма, учитывать:
  - серверную валидацию
  - отображение ошибок
  - сохранение введённых значений
  - работу тёмной темы
  - адаптивность
- Если меняется таблица:
  - следить, чтобы важные поля помещались
  - не ломать мобильную/планшетную версию
  - не ухудшать читаемость

### API / Webhooks / Bot integrations
- Проверять идемпотентность, таймауты, повторную доставку, логирование ошибок и обработку невалидных payload.
- Не допускать утечки секретов, токенов и чувствительных данных в логах.
- Если есть callback/webhook flow, явно проверять:
  - дедупликацию
  - валидацию входных данных
  - трассировку request id
  - корректные ответы внешней системе
  - устойчивость к отсутствующим полям

### Docker / Infra
- Не ухудшать production-конфигурацию ради dev-удобства.
- Не смешивать dev bind mounts и prod run strategy.
- Учитывать healthchecks, restart policy, volume strategy, logs, collectstatic, migrations.
- Если меняется compose или Dockerfile, объяснять зачем именно это нужно.
- Любые изменения nginx должны быть минимальными и обоснованными.

### Logging
- Поддерживать разделение логов по смыслу:
  - django/app
  - requests
  - security
  - integrations/webhooks
  - background/jobs
- Поддерживать rotation и пригодность логов для расследования проблем.
- Никогда не логировать секреты целиком.

### Security
- Проверять auth, permissions, csrf, input validation, object-level access.
- Искать небезопасные debug endpoints, открытые служебные routes, прямые вызовы без auth.
- Для внешних интеграций не доверять входным данным.
- Не предлагать отключение безопасности как “решение”, кроме локального dev и только если это явно отмечено.

## Правила изменения кода

1. Любая новая функция или метод должны иметь внятное имя.
2. Любой новый модуль должен появляться только если он реально улучшает структуру.
3. Не создавать “helpers.py”, “utils2.py”, “final_service.py”, “new_views.py”.
4. Не оставлять мёртвый код, закомментированные блоки, временные хаки и TODO без контекста.
5. При изменении модели:
   - оценить влияние на миграции
   - оценить влияние на admin, forms, filters, serializers, templates, tests
6. При изменении полей формы:
   - проверить initial/data формат
   - проверить binding при POST
   - проверить отображение ошибок
7. При изменении template:
   - проверить, что все используемые context variables реально существуют
   - не вводить логику, которую правильнее держать в view/service
8. При изменении JS/CSS:
   - не ломать существующие data-атрибуты, id и hooks без необходимости
   - не делать визуальный регресс ради “красоты”

## Работа с тестами

- Перед завершением задачи Codex должен определить, какие тесты релевантны.
- Если задача меняет поведение, Codex должен добавить или обновить тесты.
- Предпочтение:
  - unit tests для бизнес-логики
  - integration tests для critical flow
  - regression tests для найденных багов
- Не писать тесты “ради галочки”.
- Если тесты невозможно добавить быстро, явно указать, что именно осталось без покрытия и почему.

---

## Проверки перед завершением задачи

Codex должен по возможности запускать релевантные проверки из списка:
- pytest
- python manage.py check
- python manage.py test
- python manage.py makemigrations --check --dry-run
- ruff check .
- python -m compileall .

Если часть команд отсутствует в проекте, не придумывать их наличие, а использовать только реально доступные.

## Формат результата для сложных задач

При нетривиальных задачах отвечать в таком порядке:

1. Что было изучено
2. Как сейчас работает участок
3. В чём проблема или цель
4. Какое решение выбрано и почему
5. Какие файлы изменены
6. Какие риски остаются
7. Что и как проверено

---

## Что запрещено

- Не переписывать половину проекта без запроса.
- Не менять стиль кодовой базы “под себя”.
- Не внедрять новую библиотеку, если задача решается текущим стеком.
- Не менять public behavior без явного объяснения.
- Не удалять существующие проверки безопасности без веской причины.
- Не скрывать риски миграций, прод-эффектов и побочных изменений.
- Не делать вид, что “всё проверено”, если проверки не запускались.

---

## Definition of Done

Задача считается завершённой, когда:
1. Изменение встроено в текущую архитектуру проекта.
2. Нет явных регрессий в связанных участках.
3. Добавлены или обновлены тесты там, где это оправдано.
4. Учтены безопасность, права доступа и UX.
5. Даны чёткие notes по проверке результата.
