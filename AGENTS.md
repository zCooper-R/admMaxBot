# AGENTS.md

## Контекст проекта
Проект — монолит на Django с модульной структурой приложений:
- `apps/accounts`
- `apps/analytics`
- `apps/audit`
- `apps/bot`
- `apps/core`
- `apps/dashboard`
- `apps/max_integration`
- `apps/menu_builder`
- `apps/webhooks`

Ключевые особенности:
- backend + русскоязычная web-панель управления;
- webhook endpoint и внешняя интеграция через `apps/max_integration`;
- service-oriented подход внутри приложений (`services.py` в нескольких apps);
- локально база SQLite, в Docker используется Postgres;
- инфраструктура через `Dockerfile`, `docker-compose.yml`, `docker-compose.prod.yml`, `docker/entrypoint.sh`;
- есть unit и integration тесты в `tests/`.

## Главные правила работы
1. Делать минимально достаточные изменения в существующем паттерне проекта.
2. Не переносить логику между apps без явной архитектурной причины.
3. Сначала анализировать существующие services/forms/views/templates/tests, затем менять.
4. Не выполнять широкий рефакторинг вместе с bugfix/feature, если это не запрошено явно.
5. Весь новый контент в репозитории — на русском языке, если нет специального требования иначе.

## Архитектурные ориентиры по текущему проекту
- Точки входа маршрутов собраны в `config/urls.py`.
- Настройки и env-конфигурация — `config/settings.py`.
- Webhook обработка и idempotency-контур — `apps/webhooks/services.py` и `apps/webhooks/views.py`.
- Интеграционные вызовы во внешний API — `apps/max_integration/*`.
- UI панели: `templates/*`, базовый layout и JS hooks — `templates/base.html`, стили — `static/css/app.css`.

## Изменения в Django-слое
- Для бизнес-логики предпочитать `services.py`/существующие слои, не перегружать views.
- Для read-path проверять QuerySet-поведение и N+1 (`select_related`, `prefetch_related`).
- При изменениях в models:
  - оценивать миграции и обратную совместимость;
  - проверять влияние на forms/views/templates/admin/tests.
- Для форм:
  - проверять bind на GET/POST;
  - server-side validation;
  - сохранение введенных данных при ошибках;
  - корректный рендер ошибок.
- Formsets сейчас не выделены как отдельный слой; если добавляются, тестировать prefixes и согласованность management form.

## Webhook и integrations (обязательный контроль)
Любые изменения в `apps/webhooks` и `apps/max_integration` требуют проверки:
1. Идемпотентность и duplicate delivery.
2. Валидация входящего запроса и секрета (`X-Max-Bot-Api-Secret`).
3. Таймауты, retries и устойчивость к неполному payload.
4. Безопасное логирование (без утечек токенов/секретов).
5. Корректные HTTP-ответы внешней системе.
6. Трассируемость через request id / структурные логи.

## Templates/Admin UI
- Не ломать существующие JS hooks, `id`, `data-*` атрибуты.
- Сохранять админскую пригодность экранов: таблицы, фильтры, формы, сообщения об ошибках.
- Учитывать адаптивность и поддержку темной темы (в проекте уже есть переключение темы).
- Не ухудшать русскоязычный UX и читаемость интерфейса.

## Docker и окружения
- Локальная разработка: `.venv` + SQLite.
- Docker окружение: Postgres в compose.
- Не смешивать dev/prod стратегии запуска.
- Любые изменения `Dockerfile`, compose и entrypoint должны учитывать:
  - startup flow (wait/check db, migrate, collectstatic, app start);
  - healthchecks;
  - volumes и writable dirs;
  - безопасное хранение секретов.
- В репозитории нет nginx-конфига; не добавлять предположения о reverse proxy без фактической необходимости.

## Логирование и безопасность
- Сохранять структурированный лог-формат проекта.
- Не логировать секреты целиком.
- Проверять auth/permissions/object-level доступ при каждом изменении endpoint.
- Не ослаблять security-настройки ради временного удобства.

## Тестовая стратегия
- Следовать существующей структуре тестов: `tests/unit` и `tests/integration`.
- Для bugfix обязательно добавлять регрессионный тест.
- Для изменений webhook/permissions/forms — добавлять целевые проверки.
- Использовать виртуальное окружение проекта для запусков:
  - `.\.venv\Scripts\python -m pytest -q`
  - `.\.venv\Scripts\python manage.py check`

## Definition of Done
Задача завершена, когда:
1. Изменение внедрено в текущую архитектуру без лишнего рефакторинга.
2. Покрыты критичные риски (correctness/security/regression/performance).
3. Обновлены или добавлены релевантные тесты.
4. Проверки из `.venv` выполнены и результат зафиксирован.
5. Даны понятные notes по ограничениям и дальнейшим шагам.

## Формат отчета для сложной задачи
1. Что проанализировано.
2. Текущее поведение.
3. Проблема/цель.
4. Решение и его границы.
5. Измененные файлы.
6. Риски и что осталось вне scope.
7. Какие проверки выполнены и с каким итогом.
